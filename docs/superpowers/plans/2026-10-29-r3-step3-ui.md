# R3 — bod 3: dostupné diagnostiky a odolnější pracovní plocha

Datum: 29. října 2026. Výchozí checkpoint `fe53a0d`, větev
`feat/r3-electron-workspace`. Rozsah je pouze pokračovací bod 3 z
`2026-10-11-r3-progress.md`; body 4–6, R4 a autorské přijetí zůstávají samostatné.

## Výsledné chování

- **Diagnostika R0:** tlačítko v levém panelu otevře dialog s explicitním
  spuštěním existující diagnostické služby. Zobrazí skutečný souhrn a jednotlivé
  stavy „Prošlo“, „Selhalo“, „Přeskočeno“, bezpečné zprávy, kódy a technické
  důkazy. Opakovaný klik za běhu nevytvoří další požadavek; chyba umožní nový
  explicitní pokus. Zavření dialogu nespouští ani neopakuje kontrolu.
  Používá se existující `runR0Diagnostics` v preloadu a existující R0 IPC kanál.
  Rendererový klient navíc validuje požadavek i odpověď sdílenými schématy.
- **Vytížená nastavení:** po backendovém `R3_PROJECT_BUSY` nabídnou přímý
  návrat k aktivnímu běhu. Funguje i po obnovení rendereru při vybraném jiném
  chatu. Tlačítko Zastavit se zobrazí teprve podle nově připojeného backendového
  snapshotu; mezitím dokončený běh jej nevytvoří. Pokud již žádný běh není,
  nastavení ukážou čitelnou zprávu a zůstanou zavíratelná.
- **Editovatelné opakování:** „Nový pokus“ u selhaného, zastaveného či
  přerušeného běhu pouze vloží původní zadání do composeru a zaměří jej.
  Uživatel ho může upravit a musí sám odeslat. Nový požadavek dostane nové
  `requestId` a vazbu `retryOfRequestId`. Při ztracené odpovědi se zachová
  identita i celá již odeslaná obálka včetně režimu a limitu kroků až do
  potvrzení přijetí. Prokazatelně nový pokus vytvoří novou obálku. Text,
  metadata i rozpracované požadavky patří konkrétnímu chatu.
- **Starší aktivita:** průběžný snapshot již nepřepíše načtené starší stránky.
  Položky se slučují podle event ID a řadí podle sekvence; překryv není
  duplikován a poslední dosažený starší kurzor se zachová. Změna chatu,
  požadavku běhu či přechod mezi aktuálním a historickým detailem tvoří nový
  rozsah. Opožděná stránka z předchozího rozsahu se ignoruje. Během načítání
  se druhá stejná stránka nespouští.

Zachovány jsou Instrument Sans, lesní zelená, světlé/tmavé panely, zaoblení
i vlastní SVG ikony. CSS ani schválená vizuální baseline se neměnily.

## Úzké doplnění kontraktu

Existující `r3:invoke` nově přijímá `run.active` bez privilegovaných vstupů.
Vrací pouze `null` nebo `{projectId, chatId, jobId}` z živé backendové mapy
`DesktopRunManager`. U více běžících projektů poskytne jednu aktivní
navigační identitu. Renderer poté připojí jediný chat obvyklou cestou.

Důvod: lokální zapamatování aktivního chatu nepokrývá obnovu rendereru.
Prohledávání všech historických chatů přes `chat.snapshot` by opakovaně
spouštělo filesystem/Git refresh. Nový dotaz nedělá takový scan a neobsahuje
obsah projektu, klíče ani orchestrace či bezpečnostní rozhodnutí v rendereru.
Požadavek i výstup mají striktní sdílené schema; IPC kontrola odesílatele se
nemění. Regrese ověřuje odmítnutí dodatečné cesty i neočekávaných výstupních
dat a nepřítomnost snapshot volání. Skutečný manager test ověřuje identitu
mezi přijetím a dokončením běhu i následné `null`.

## Oprava po nezávislém review — kolo 1

Review potvrdilo P2 závod ve stejném chatu: při čekání na odpověď
`run.submit` šlo znovu připravit „Nový pokus“. Nový koncept měl vlastní
identitu, ale dokončení staršího odeslání čistilo mapu i textarea pouze
podle chat ID, takže novější koncept smazalo. Opožděná chyba také mohla
nesprávně označit novější koncept za neúspěšně odeslaný.

Úzká oprava v `apps/desktop/src/renderer/components/composer.tsx`, řádky 9–11:
odeslání zachytí identitu konkrétního draft objektu a attempt objektu.
Přijetí vymaže jen ty objekty, které stále vlastní; textarea a retry metadata
vyčistí pouze při shodě potvrzeného konceptu. Opožděná chyba se zobrazí jen
u téhož dosud aktuálního konceptu. Novější koncept zůstává zachovaný,
neodesílá se automaticky a jeho pozdější explicitní odeslání dostane nové
request ID i původní retry vazbu.

Přímá regrese v `apps/desktop/test/composer.test.tsx`, řádky 27–35, pokrývá
opožděné přijetí i odmítnutí. Používá dvě různé identity konceptu se stejným
textem, takže neprojde pouhé porovnání chat ID nebo obsahu. Kontroluje
zachování textu, absenci staré chyby, žádný automatický submit a nové ID
při následném explicitním odeslání.

Příkaz před opravou i po ní:

```powershell
npm.cmd exec -- vitest run apps/desktop/test/composer.test.tsx apps/desktop/test/workspace.test.tsx --reporter=dot
```

- Červená fáze: **2 failed / 13 passed**. Přijetí smazalo „Stejné zadání“;
  odmítnutí přidalo starou chybu k novému konceptu.
- Zelená fáze: **2 soubory / 15 passed**, **4,78 s**.

Toto kolo změnilo pouze Composer, jeho přímý regresní test a tento report.
Další úplná sada, statické kontroly a omezené opakované review patří
rodičovskému úkolu. Nové screenshoty ani další funkční změny nevznikly.

## Zachované hranice a zbývající práce

Renderer neimportuje filesystem, Node, SQLite ani procesní API. Permission,
recovery, stop a skutečné diagnostické výsledky nadále vlastní backend.
Nevznikly skutečné API požadavky, klíče ani síťová modelová volání.

V tomto kroku se nespouštěl nový Electron package, packaged smoke,
`verify:r3`, úplný Electron UI E2E ani live modelový protokol. Žádný starý
zabalený executable neslouží jako důkaz této změny. Autorské přijetí, body
4–6 a celý R3/O1 se tímto neuzavírají. Implementer neprováděl staging ani
commit; zkontrolované změny ukládá rodičovský úkol podle AGENTS.md. Push ani
PR se v tomto kroku neprovádějí.
